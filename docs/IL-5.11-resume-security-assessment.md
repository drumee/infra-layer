## B2 — Correctif et contrat image

Le motif initial permettait de répartir les mêmes caractères entre `[a-zA-Z0-9._/-]+` et `[a-zA-Z0-9._/-]*`, et les chiffres entre le port et la fin de référence. Le nombre de répartitions rend le rejet quadratique. Aucun appel ne borne la longueur. Le défaut est exploitable en déni de service synchrone par un consommateur local acceptant une configuration non fiable ; aucune exposition HTTP native de ce paramètre n’est démontrée.

`pinnedImage`, fonction privée au fichier lib/validation.js, localise le suffixe fixe puis partitionne la référence au premier deux-points avant de valider des composants simples disjoints. Chaque scan est linéaire, le digest fait exactement 64 caractères hexadécimaux minuscules. Pas de regex complexe déplacée, de dépendance ou d’export ajouté. Les références sans suffixe numérique et avec les tags numériques historiquement admis restent acceptées ; les tags nommés, deux-points multiples, caractères interdits et digests incorrects restent refusés. Les terminaisons de ligne que `$` tolérait accidentellement sont désormais rejetées : elles ne sont pas un format de référence Docker valide/documenté. Aucun élargissement du format ni nouveau plafond de taille ; types, signatures et code INCOMPATIBLE_ADAPTER_CONFIGURATION / champ adapter.image inchangés.

La reproduction publique API est rejouée dans des processus isolés avec CPU 2 s, temps mural 3 s, heap JS 64 MiB, 64 descripteurs et environnement minimal : [script](evidence/IL-5.11-resume/image-validation-cost.py), [mesures avant/après](evidence/IL-5.11-resume/B-redos-bounded.json). Deux familles, avec et sans deux-points, croissent jusqu’à 65536 caractères. Les cas baseline atteignent la limite CPU ; le candidat les refuse en quelques millisecondes, y compris le coût du plan public. La régression million de caractères a un timeout de processus 3 s ; une longue référence valide reste acceptée. Les tests couvrent images/digests, grammaire préservée, tags, caractères interdits et codes owning. Aucun durcissement d’un composant externe requis.

## B3 — Usages exacts de digest

Tous les appels S.digest de production sont consignés dans B-digest-calls.txt. Catégories : DNS (texte de zone et manifestes), Redis (configuration client privée), TLS (certificats publics), plans v1/v2 (descripteurs/rendus/révisions), rendu (contenu d’artefacts existants), composition/préparation (descripteurs de mounts et références, attestations, révisions), activation (description de jobs et attestations), journal (chaîne d’intégrité), sauvegarde/restauration (manifestes). Les métadonnées de projection hachées comportent des références/chemins, pas les valeurs lues du store. Aucun alias de production n’est utilisé comme password verifier.

**Exception de sensibilité explicitement examinée :** capabilities/redis/index.js:20–28 lit le secret Redis pour produire redis-config.json ; le SHA256 porte donc aussi sur le credential incorporé à cette configuration. Le digest n’est pas utilisé pour authentifier un utilisateur ou vérifier un mot de passe fourni. Il compare le contenu complet d’un fichier possédé, conjointement à l’égalité byte-à-byte du contenu attendu. Le répertoire est privé (0700), fichiers/config/marker atomiques privés (0600), accès explicitement autorisé et store scoped consumer redis ; le hash ne révèle pas à un lecteur du marker un secret qu’il ne peut déjà lire dans le même répertoire protégé. Aucun hash de ce contenu n’est exporté comme vérificateur de login. Le résultat rendu à l’appelant est la référence et le fingerprint du store, pas le digest du marker.

SHA256 est adapté à cette empreinte de contenu et aux révisions canoniques. Il n’est ni une KDF ni un MAC contre un propriétaire malveillant. Le store utilise aussi SHA256 pour détecter la corruption de secrets, et les véritables services reçoivent les credentials par projections privées ; cela ne constitue pas une base de mots de passe utilisateurs. Les contrôles d’ownership/at-rest restent indispensables et aucun droit n’est élargi. Ne pas remplacer SHA256 par Argon2/scrypt/bcrypt : cela changerait le contrat des révisions sans corriger un password storage inexistant. Disposition du diagnostic js/insufficient-password-hash : **FALSE_POSITIVE_TECHNICALLY_CONFIRMED**, avec cette analyse de sensibilité, pas avec une prétendue absence de toute entrée secrète.

## B4 — RSA-1024

La clé est générée en mémoire dans un test négatif, jamais distribuée ni employée par un service. Le test attend SECRET_CORRUPTED. validateValue est commun à import, génération, rotation et lecture de génération : RSA <2048 bits est refusé pour tls-ca-key, tls-leaf-key, acme-account-key et dkim-key. Les générations réelles utilisent RSA-2048 ; les courbes EC sont explicitement allowlistées et DKIM exige RSA.

Le test supplémentaire conserve RSA-1024 et vérifie les quatre types, l’absence de secret/manifest après import refusé, le refus de rotation et l’identité de la génération précédente. Le store peut créer ses répertoires 0700 avant validation ; aucun octet de clé faible n’y est commis. Les Buffer/KeyObject vivent le temps du processus de test, sans garantie de zeroization JS ; fixture mkdtemp et descendants supprimés par t.after. Pas de voie alternative constatée pour accepter une clé faible. Disposition : **FALSE_POSITIVE_TECHNICALLY_CONFIRMED / TEST_NEGATIVE_CONFIRMED**.
