# Strict direct-child observer shutdown contract

Gate B contract. Two process boundaries are distinct: campaign Node parent → private IPC Node observer → directly spawned /usr/bin/docker events CLI. The outer Node wrapper must exit0 with drained stdout/stderr and matching exit/close; wrapper143 is never a valid substitute. Only the directly bound Docker events CLI may report the143 representation qualified by this contract.

States: NOT_STARTED → STARTING (held ChildProcess object/PID/spawnfile/spawnargs captured) → COLLECTING (spawn event, pipes attached) → COLLECTION_COMPLETE → STOP_REQUESTED → TERMINATED. A persistent first error changes state to FAILED; later cleanup cannot restore success. Native normal0 without a stop is allowed only after COLLECTION_COMPLETE; live-stream premature0/143/signals fail. Duplicate starts/stops, stale PID, mismatched child object or changed executable/argv fail without another normal shutdown signal. At worker protocol level, a duplicate completion is fatal and may trigger separately logged failure-abort cleanup on the same held child; that cannot become accepted shutdown or target another PID.

COLLECTING readiness means successful CLI spawn/stream attachment, not an invented Docker subscription ACK. The Node worker atomically writes a private identity-bound ready receipt. An event-driven fs.watch barrier in a short helper waits for both exact receipts before the canonical child starts. This accommodates the existing synchronous runner without polling sleeps or case reordering. Event replay since attempt start plus mandatory coverage is separately verified; readiness alone cannot qualify evidence.

Collection cutoff: original Services child has a valid terminal result;17 case starts/completions are present; every host capture operation has exactly one terminal record; no case/shutdown/exit pending or cross-case completion; capture process/listener/handler/finish/normal-exit chains are complete; owned Compose down succeeds and no main containers remain. Required daemon observations include initial/final inspected container IDs with create/start/die/destroy, at least18 main and3 ephemeral creates from the fixed canonical operation inventory, and complete create/start/die/destroy for every observed created container. This is a scoped lifecycle coverage contract, not a claim that every daemon exec notification or unrelated event is collected. Container restart may produce extra starts. Collection remains open until required trailing destruction records arrive.

The parent records an identity-bound completion intent before IPC send. The private fork channel carries attempt UUID, observer instance token and exact Node PID; the worker verifies all three and refuses duplicate/early/malformed completion. Only after required coverage does it record COLLECTION_COMPLETE and a CLI SIGTERM intent with exact held child PID/executable, then invoke that same ChildProcess.kill(SIGTERM), recording its actual boolean result. No PID name lookup, process-group signal or arbitrary executable is used.

CLI exit is evidence of termination, not stream completion. The worker records exit and close separately and requires identical tuples plus stdout/stderr end+close, no partial JSON, zero stderr bytes, no parse/collection/stream/spawn error, complete coverage and successful signal delivery. Only then may controlled signal-form SIGTERM, direct Docker143/null, or controlled graceful0/null be accepted. Unsolicited143/SIGTERM, unexpected SIGKILL/nonzero, prior error and missing observations remain fatal. Numeric143 is not accepted for an unverified wrapper. Any stderr is fatal; only byte count/hash is retained, never raw text.

The parent independently requires collecting receipt, its prior completion intent, accepted coverage/signal/stream result, same worker/CLI identities, wrapper exit0/close0 and drained wrapper streams with no unexpected stdout/stderr. Both mandatory observer results are required. Services failure and earlier campaign failure are retained separately and remain fatal even if observers clean up successfully. Final success also requires the canonical owned filesystem removal and no earlier orchestrator error.

Watchdogs:15s startup/readiness,15s after completion request for trailing coverage+termination+stream closure. These bounds reuse the diagnostic Docker command bound; the readiness helper outer process has16s solely to let its15s refusal report/close. No existing Services/fetch timeout is increased. These are failure deadlines, not sleeps or retry windows. Timeout is fatal; only best-effort SIGTERM to the exact owned child is used, with no SIGKILL escalation. A remaining process makes cleanup fail and cannot yield qualification. Tests model deadline expiration deterministically; real positives use event handshakes, not timing delays.

[Node22.22 child-process contract](https://nodejs.org/download/release/v22.22.0/docs/api/child_process.html): kill success does not prove termination, exit does not prove streams closed, and code/signal are separate observations. Per-process sequences order intent/send/exit/close; no cross-process millisecond inference is made. Qualification will separately verify the actual pinned Docker CLI representation rather than infer it from the number143.

## PID field interpretation

The reused P1 logger combines base metadata with caller fields. Contract rows carrying `pid` refer to the **target Docker CLI**, while `process_instance` and sequence identify the emitting Node worker. Ready receipts and parent records explicitly retain observer_pid and cli_pid; result.pid is the CLI. This naming limitation is documented rather than rewriting recorded evidence. It does not provide a PID lookup target: signals use the held ChildProcess object and its captured identity. Per-process ordering uses process_instance/sequence, not an assumption that every row.pid is the emitter.
