# Canonical Services architecture

Gate B PASS by complete source inventory. Canonical command `npm run test:services` resolves to `node test/services/run.js`; original aggregate `npm run test:integration` ran gateway first, Services next, and stops after a failing child. These are separate processes/projects, not a shared JavaScript pool. P2 intentionally covers the complete Services environment only, not the preceding Gateway campaign.

Runner prepares one fresh Docker project, dynamic loopback ports, shared plan/store, TLS/projections, capture/data directories and rendered Compose; launches services via Compose up --wait; then synchronously runs one Node --test file. That file defines17 top-level cases with no concurrency option or subtests. Node's default runs them sequentially in one worker/application thread, sharing global metadata, mutable plan, secret-store handle, process environment and built-in fetch dispatcher. File-level process isolation does not isolate cases within that file. Native hook control and campaign case events will verify order without adding a concurrency flag.

All cases inherit IL2_METADATA pointing to one metadata file and working directory at repo root; its ports, fixtures, compose_file, plan_file, keys, relay_ref and runtime_redis path remain shared. The Node child for case11 receives the fixed runtime source and credential directory under the same owned root, and exits before its parent command returns. No AbortController or per-case HTTP cleanup is defined. All literal asynchronous test callbacks return their Promise to node:test; calls to top-level test() register tests without awaiting registration, which is the native test-runner contract.

The test node thread has one reusable capture HTTP client pool across13–16. Capture is a single Node process combining HTTP8025 and SMTP2525; HTTP host port is dynamic and loopback-only. Initial service readiness uses a separate Node process per Docker healthcheck. DNS host port serves TCP/UDP1053; database3306, Redis6379, mail2525 have their own dynamic host publications. Mail has declared kernel+mail-control networks; DKIM only internal mail-control; capture/DNS/DB/Redis use kernel. Every actual ID/port must come from campaign metadata/events rather than historical IDs.
